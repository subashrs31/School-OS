# Sub-phase 2.1 — Staged identity, RBAC and tenancy foundation

**Status:** ✅ Implemented 2026-09-30 · **Type:** schema foundation (additive, no behaviour change)
**Depends on:** 2.0-P (PostgreSQL + Prisma port) · **Decisions:** ADR-001…005, ADR-007 · **Rules:** [prisma-migrations.md](../prisma-migrations.md)

> **Revised 2026-09-30.** The first version of this spec (written before the port) created the identity and tenancy
> tables from nothing and turned `users` into a password-less profile. After the port those tables already exist and
> the running backend still signs people in with `users.password` until Phase 4 moves sign-in to the license server.
> The owner chose a **staged** 2.1: add the design's structures next to the existing columns, remove the old ones in
> the phases that stop using them. Database columns stay **camelCase** (owner decision).

## 1. Requirement
Lay the schema foundation that Phase 4 (sign-in through the license server, scoped authorization), the
license-server integration (LS-4/LS-5) and ADR-007 (self-service sign-up) need — **without changing what the running
API does**.

## 2. What was added

| Table | Added | Used by |
|---|---|---|
| `users` | `publicId` (UUID, unique, DB default), `identitySubject` (unique, license-server `sub`), `accountPlane` (PLATFORM/SCHOOL, default SCHOOL), `accessVersion` (default 1) | 4.1, ADR-003 §6 |
| `organizations` | `publicId` (UUID, unique = tenant id in the license server), `status` (PENDING/ACTIVE/INACTIVE/SUSPENDED/CLOSED, default ACTIVE), `statusSource` (MANUAL/SUBSCRIPTION), `statusReason`, `statusChangedAt`, `statusChangedBy`, `signupSource` (PLATFORM/SELF_SERVICE), `onboardedBy`, `activatedAt` | LS-4/5, 4.6, 5.1, ADR-007 |
| `branches` | unique `(organizationId, id)` — the pair key scoped rows reference | design §2 isolation wall |
| `permissions` | `module` (nullable until 4.4), `isSensitive`, `isPlatformOnly` (default false) | 4.4, licence plan gating |
| `user_has_roles` | `scopeType` value `branch`; `organizationId` (FK), `branchId` (**pair FK** → `branches(organizationId, id)`), `validFrom`, `validTo`, `grantedBy`, `grantedAt`, `revokedAt`, `revokedBy`, `revokeReason` | 4.3 |
| `user_has_permissions` | `organizationId`, `branchId` (same FKs), `reason`, `grantedBy`, `grantedAt`, `revokedAt` | 4.3/4.4 |
| `audit_logs` (new) | design §4.9 columns; indexes `(organizationId, occurredAt)` and `(occurredAt)`; **no FKs** (audit outlives what it describes); **append-only trigger** | 4.4, 4.6 |

Design-name mapping (the design doc's names → this schema): roles `key` → `slug`, roles `status` → `isActive`,
users `display_name` → `name`, `*_by` columns → plain references (`grantedBy`, …) like the existing `assignedBy`, per
design §10.

## 3. Decisions not obvious from the diff
1. **Additive only.** Every new column is nullable or has a default, so the ported rows and the running services are
   untouched. `organizations.isActive` stays authoritative until 5.1; `status` is backfilled from it.
2. **System-managed columns never come from request bodies.** `modelData()` (the helper that copies request bodies
   into Prisma data) now ignores `publicId`, `identitySubject`, `accessVersion`, `accountPlane`, the status bookkeeping,
   `signupSource`, `onboardedBy`, `activatedAt`, the grant/revoke history, `module`, `isSensitive`, `isPlatformOnly`.
   `organization.service` also excludes `status` (only the lifecycle in 5.1 and licence webhooks in 4.6 may change it).
   Without this, every new column would have become writable through the existing update endpoints.
3. **No CHECK constraints yet** on the scope columns or on `roleType`/`isSystem`: current endpoints can still create
   rows those checks would reject, which would turn into 500s. They arrive in 4.3/4.4 together with validation and
   the code that writes the new columns (with a second backfill).
4. **Pair foreign key** `(organizationId, branchId) → branches(organizationId, id)`: PostgreSQL itself refuses a
   branch-scoped assignment that points at another school's branch.
5. **`audit_logs` has no foreign keys** and a trigger that rejects `UPDATE`/`DELETE`; `TRUNCATE` (test helper only)
   is not a row operation and is allowed.

## 7. How the migration was produced (recorded exception)
`prisma migrate dev --create-only` refuses to run in a non-interactive shell when it has warnings to confirm (here:
four new unique constraints, all safe). At the owner's explicit request ("you run it yourself and check") the
assistant generated the SQL with `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma
--script` (after confirming the dev database had no drift), appended the reviewed backfill and trigger SQL, and applied
it with `prisma migrate deploy` to `school_os` and `npm run db:test:migrate` to `school_os_test`. This is the second
recorded exception to the owner-runs-migrations rule (see `prisma-migrations.md`).

## 8. API impact
Additive only: organization, user, role-assignment and permission responses now include the new fields (for example
`publicId`, `status`, `accountPlane`). No field was removed or renamed. `/auth/me` is hand-built and unchanged.

## 9. Rollback
Revert the commit and remove the migration folder before it is applied anywhere else; on the local databases, the
owner drops and recreates `school_os` / `school_os_test` and re-applies the remaining migrations. (Local data only.)

## 10. Non-technical summary
We added the database fields the next steps need — a permanent ID for every school and user, a school status
(active, suspended, …), a way to give someone a role in just one branch, and a tamper-proof activity log — without
changing how the app behaves today. The existing screens work exactly as before, and 274 automated checks pass.
